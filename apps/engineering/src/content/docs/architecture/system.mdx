The main application is a TypeScript modular service: a Hono API and React/Vite
assets share domain operations. The native companion and MCP handler call those
same operations. Private PDF processing and external transport adapters sit across
explicit boundaries; they do not own approval or quota decisions.

## Runtime responsibilities

| Component | Owns | Boundary |
| --- | --- | --- |
| Application Worker | Authentication, route contracts and service orchestration | Every private operation resolves current actor and workspace authority |
| D1 | Membership, immutable versions, dispatches, approvals, budgets, outbox and durable events | Constraints and transactional writes enforce business commitments |
| R2 | Exact private PDFs and source objects | An object key alone grants no access; reads remain authorized |
| Document Worker | Isolated rendering, page review and postal document checks | Explicit private bindings and bounded inputs/outputs |
| Scanner | Antivirus verification of the exact submitted bytes | Missing, stale or mismatched proof cannot promote a PDF to ready |
| PDF validator | Separate PDF conformance/accessibility diagnostics | Diagnostics do not replace security verification or modify originals |
| Queues and consumers | Asynchronous provider work from durable references | Duplicate messages do not create unconditional duplicate attempts |
| Provider adapters | Fax, email and postal request/response translation | Enabled configuration is necessary but does not itself approve a dispatch |

The application can run production rules against synthetic local data for tests.
That execution mode is distinct from contacting a hosted provider. The independent
browser-only preview has no business bindings at all.

## Why D1 is the commitment boundary

A communication must not be queued without a matching approval and reservation.
Acceptance therefore commits the dispatch transition, quota reservation and outbox
row atomically. SQL constraints and triggers participate in that invariant; moving
one check into a client would weaken it.

An outbox publisher transfers persisted work to an interactive or bulk queue.
Publication may repeat after a lost acknowledgement. A consumer conditionally
claims the eligible dispatch and records an attempt before contacting a provider.
The [dispatch lifecycle](/architecture/dispatch-lifecycle/) explains the states
and the treatment of uncertainty.

<GutenbergNote pose="review" title="The ledger outlives the messenger">
  D1 records the commitment; the queue carries the work. If an acknowledgement
  disappears, the durable record still determines what may happen next.
</GutenbergNote>

## Private processing is a separate trust boundary

PDFs and source archives are untrusted input. The API bounds input before heavier
processing; private services return bounded verification/rendering results tied
to the expected bytes. Rendering a document creates a new immutable object rather
than editing an original already used by a dispatch.

Service bindings are intentional private connections. They are not an invitation
to accept arbitrary user-supplied service URLs. Public HTTPS import has its own
egress and redirect rules, separate from private scanner/renderer access.

## Identity and external systems

Auth0 supplies identity/OAuth tokens. Current membership, connection binding,
revocation, role permissions and any delegation remain application decisions.
Telnyx, Pingen and Resend/SES adapters supply transport facts; their responses do
not overwrite the approval model. Verified callbacks become durable events before
status projection.

The [status service](https://status.guteneo.com/) is independently deployed and
observes bounded public endpoints. Its health observations are not access to
customer documents or proof that an authenticated delivery journey succeeds.
This engineering site is a static documentation surface with no business binding.
The separate [Belvédère administration](/administration/belvedere/) guide explains
platform oversight, its metadata-only projections and its operator authority.

## Location and qualification

The checked-in configuration uses EU jurisdiction for relevant D1/R2 resources.
That setting is not a claim that all identity, browser execution, provider,
subprocessor, log or backup processing occurs in Europe. Runtime configuration,
external contracts and actual hosted journeys require their own qualification.
