# Guteneo 1.2.5 — Gare browser experience

This candidate continues the separate station experience in `apps/experience`
and includes the unpublished [1.2.4 candidate](https://github.com/nclsppr/guteneo/blob/main/docs/releases/1.2.4.md).
Gare has its own static build and intended origin, `https://gare.guteneo.com`,
while the existing application and API remain canonical at `https://guteneo.com`.

## What changes

- A public hall and authenticated station navigation cover dispatches, the
  preparation counter, workspace PDFs, personal arrivals, secure distributions,
  saved recipients, schedules, templates, workspace usage and account controls.
  The interface supports French, English, German and Luxembourgish, light and
  dark appearance, narrow screens and reduced motion.
- Eligible plain-text email has an exact native review with explicit content
  consent and the required recipient-request attestation. It uses the existing
  fingerprint-bound approval and confirmation endpoints. Complex documents,
  custom HTML, postal/secure options, scheduled holds and specialist editors
  continue through clearly identified canonical interfaces.
- Session changes invalidate in-flight work and private views. Reads are bound
  to the current person, workspace, permissions and document policy; stale
  responses cannot repopulate another account. Uncertain writes require an
  explicit status check and never trigger an automatic duplicate submission.
- The canonical backend accepts credentialed browser requests only from the
  exact configured same-site Gare origin, retaining host-only cookies, CSRF and
  current authorization. Sign-in keeps the canonical Auth0 callback and uses a
  bounded return path to Gare.
- Static publication checks source, build configuration, asset bytes, response
  headers, backend activation and served content. The asset deployment has no
  database, storage, queue or provider binding. Existing CI now includes Gare's
  synthetic desktop/mobile inventory in its required browser evidence.

## Validation and release scope

The [experience contract](https://github.com/nclsppr/guteneo/blob/main/docs/EXPERIENCE.md)
records implementation, local checks, synthetic browser evidence and production
activation separately. Local lint, documentation checks, engineering build and
CI policy tests passed during candidate preparation. The local macOS Chromium
attempt was blocked before browser startup; it is not a passing browser result.
The actual local browser/API journey also passed demo sign-in, plain-text email
preparation, exact review and explicit simulated approval through queued status
and the accepted/accepted-by-server events.
It sent no external communication. Complete hosted CI on the exact candidate
remains a publication prerequisite.

This candidate adds no database migration or assistant tool. Application and
portable/Claude/Cursor package versions move together to 1.2.5, with synchronized
metadata and rebuilt integration archive. Existing tool schemas, scopes,
instructions, host confirmations and delegated-consent policy remain unchanged.

No real communication is sent by this qualification. Synthetic responses and
local simulation do not establish Auth0 production return, provider readiness,
delivery, billing, marketplace approval or native distribution. Custom-domain
readiness, exact backend-origin activation and authenticated hosted reads must
be verified independently before claiming a production-ready experience.
