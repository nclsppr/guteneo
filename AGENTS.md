# Guteneo engineering rules

English is the default and required language for repository-authored code, identifiers, comments, tests, documentation, diagrams, examples, integration instructions and API messages. The product-language exceptions are frontend internationalization, recipient-facing transactional interface copy and localized video content, kept in their declared resources. Preserve exact user content, external identifiers, proper names, quotations and third-party licenses. Canonical public, application and API URL paths use English; translating a label must never translate its destination. Follow [docs/REPOSITORY_STANDARDS.md](docs/REPOSITORY_STANDARDS.md) for terminology, compatibility, documentation ownership and review requirements.

Give every current rule one authoritative home and link to it instead of copying operational guidance. Reuse shared frontend shells, components, route helpers and locale keys for the same behavior; remove repeated titles, identity blocks, explanations and primary actions without hiding consent, price or recovery information. Keep the [documentation index](docs/README.md) current. Language and documentation checks must pass in the same PR as the change; generated views are edited through their source.

Cut taglines, helper text and secondary labels. If a screen needs them to make sense, fix the layout.

Make the best decision that will elevate all three: the user experience (UX), developer experience (DX), and agent experience (AX) always, without breaking anything.

For every new or changed frontend page, challenge its loading path and apply performance best practices. Measure the relevant requests, transferred code and first useful content; remove unnecessary waterfalls, eager heavyweight dependencies and repeated work. Preserve authorization, tenant isolation, locale, account switching and recovery while improving speed. Record measured results and their environment instead of claiming an unmeasured gain.

Keep the public route registry and generated sitemap up to date whenever pages are added, moved or removed, including canonical URLs and all four language variants. Every public-site page must use the shared footer so visitors can reach product, pricing, help, legal and service-status information before entering the web application. Preserve coherent navigation and language across these pages; verify links and the sitemap with the rendered site.

Every feature addition, change or removal MUST update both the authoritative feature tree in `docs/feature-map.json` AND the affected developer documentation in the same PR, including the role/permission matrix and every affected customer journey. Cover entry conditions, actor and current authority, steps, result, errors/recovery, web/native/REST/MCP surfaces, privacy, activation gates, technical contract, source and relevant test evidence. Keep implementation, activation and deployed proof distinct. Regenerate `docs/FEATURE_MAP.md` and `docs/FEATURE_MAP.html` with `node docs/build-feature-map.mjs` and verify `node docs/build-feature-map.mjs --check` (required by CI); keep these documents readable, visually polished and consistent. The raw atlas, internal runbooks and dated evidence stay in the repository; never publish them through the product website. The separately curated Nimbus site at `engineering.guteneo.com` may publish the explicit feature projection generated by `scripts/build-engineering-content.mjs` and its authored guides. Keep `docs.guteneo.com` reserved for customer documentation. Run `npm run docs:build`, `npm run docs:check` and the engineering checks when changing this publication. Read `docs/ENGINEERING_SITE.md` for the publication boundary, visual system and maintenance contract. Four human membership roles are defined by `packages/contracts/src/roles.ts`; assistants are separate actors, never an invented fifth membership role.

Every change to GitHub Actions/CI/CD, deployment gates, Cloudflare resources or configuration, or a third-party integration MUST update the affected authored engineering guide in the same PR. Cover the execution flow, dependencies, permissions, failure/recovery behavior, operational maintenance and dated qualification limits. Keep diagrams synchronized with the implementation. Provider price changes must update the authoritative tariff source, its verification/expiry evidence and the affected maintenance guide; never copy a current price into several guides. Changes to AI instructions, design rules, internationalization, accessibility, or video production must also update their engineering guide. Repository instructions are authoritative; the public guide explains how to apply them and must not introduce contradictory permissions. Generated feature pages alone do not satisfy this requirement. See the engineering CI/release, provider maintenance, design-system, AI-contribution and video-production guides under `apps/engineering/src/content/docs/engineering/` and the maintenance contract in `docs/REPOSITORY_STANDARDS.md`.

Cloudflare cost optimisation is a standing engineering requirement. Measure CPU,
memory, startup, active time, idle time and billed requests; choose the smallest
configuration that passes representative functional, security and latency checks.
Keep instance counts bounded and avoid unnecessary wakeups, polling and repeated
work. Record current official prices, shared-account allowances and cost per
operation with clear assumptions; never claim free operation or a fixed total
bill from a quota or instance limit. Rewriting a component is permitted when
measured savings justify it and equivalent behaviour is verified. Requalify
resource and sleep changes before production; preserve document privacy, exact
bytes, authorization and process/response limits while reducing cost.

Independent SaaS; no VBS systems, accounts, secrets or production dependencies.
Never send a real communication, provision paid infrastructure, merge, or deploy production without explicit authorization.
Production fails closed on simulation, development authentication, missing scan or provider configuration.
Tenant comes from authenticated membership. All lookups, unique keys and relations are tenant scoped.
Approval binds immutable content/recipient/options/cost; an assistant cannot assert human consent.
Expert delegation is OFF by default. Only an authenticated browser administrator may grant a bounded, expiring mandate to one OAuth client; the server records delegated approval distinctly from human review. Assistants cannot enable or extend that mandate. Postal draft transfer requires its distinct delegated authority; host confirmations, scopes and provider gates remain mandatory.
Acceptance, quota reservation and outbox insertion are atomic. Unknown provider outcomes never auto-retry.
Use integer minor currency units; never log content, recipients, tokens or signed URLs.
Keep real, sandbox and deterministic simulation evidence separate.
Every MCP update must update the ChatGPT plugin in the same change: review its instructions, schemas, tool annotations and permissions, bump the synchronized package version, and rebuild and validate the downloadable `/integrations/guteneo-plugin.zip`. Never release an MCP change with a stale plugin or archive. Follow `docs/LLM_SETUP.md`; package generation does not authorize marketplace submission, merge or production deployment.

Brand lettering is lowercase and defaults to ink black: `guteneo` and a branded `guteneo.com` use the site's `--ink` color (`#181b22`), never cobalt. Blue belongs to the approved portrait, illustrations and decoration. Apply this rule to every new or revised web, email, social, video and other brand template. A standalone promotional card uses one wordmark or domain signature, never both `guteneo` and `guteneo.com`; text already present in an approved stamp counts as that signature. For web headers and application branding, the user-approved dark mode uses ivory `#f6f5ef` lettering directly on the dark surface, with white paper always retained inside the asset's actual inner blue frame in both themes. Keep the exterior, perforations and corners transparent with no added white contour; paper placement follows each source asset's geometry, not one shared inset percentage. Preserve the source image and its transparency; never place a light cartouche behind the wordmark or whole header. Light mode keeps ink-black lettering. Public-footer postmarks use ivory ink in dark mode while the printed stamp retains white paper inside and transparent exterior edges. The homepage alone retains the explicitly requested localized “Ideas travel. Ours start here.” invitation and first-dispatch action above its panorama and the common footer. The approved Luxembourg panorama appears only on the public homepage; other public pages share the same footer navigation without the panorama. Other promotional templates retain their established composition rules. Preserve the official source images. Read docs/BRAND_IDENTITY.md for asset roles and composition rules.

Reuse the approved blue swallows from `apps/web/public/luxembourg-blue-swallow-sheet.webp` as a subtle brand motif where composition space permits. Keep them few, decorative and naturally varied in scale; preserve their existing blue, with no generic bird replacements or extra logos.

The workshop, personal documents and Belvédère are three Guteneo application spaces and MUST share one design language: brand, color/theme tokens, typography, navigation geometry, controls, tables, forms, spacing and account-customization patterns. Reuse small shared components instead of creating parallel visual systems; preserve each space's authenticated authority, data scope and loading independence. Keep French, English, German and Luxembourgish behavior consistent across all three. Classic/V2 is the saved account layout choice for workshop and personal documents; Belvédère uses the V2 visual vocabulary with its separate read-only platform authority.

Main-site public routes share one 1440 px maximum outer frame with matching responsive gutters for header, main and footer; narrow prose inside that frame. Keep the same PublicFooter on every public React route, including home: compact stamp/postmark, two original decorative swallows, sixteen links and colophon. Home's large closing stamp, three birds and exclusive panorama sit above that common footer. The public header uses one appearance icon at every viewport, with a localized action name; default follows the operating system and the head bootstrap supports activation before React is ready.

Every public video and its poster must match the user's resolved interface language (French, English, German or Luxembourgish), including the personal account preference. A language change stops the previous movie. Keep every supported language in the shared public-video catalog and regenerate its media before release; never present a French movie as a localized version. Promotional and role films end with the same official V5 halftone stamp, postmark and lowercase guteneo.com card. Preserve the validated montage and use the checked-in Remotion sources and locked dependencies for regeneration.
Narration uses complete natural sentences, native ElevenLabs Enhance and method C (three contextual blocks). Prefer Manon; when unavailable or unsuitable for a language, select and record a female voice for that language. Retain the second generated variation and its real provenance. Adapt scene timings to the original speech without acceleration or removing words. Keep music at a constant gain throughout speech, pauses and the logo, preserving only the score's ending fade. Reuse immutable voice snapshots for offline renders and display each film's actual duration from the shared catalog.

Commands: npm ci; npm run db:migrate; npm run db:seed; npm run demo; npm run typecheck; npm run lint; npm test; npm run test:e2e; npm run build.
Public design preview: npm run build:preview; npm run test:preview; npm run deploy:preview. Read docs/PUBLIC_PREVIEW.md before releasing. It is a separate browser-only fixture model, with no business bindings; never expose local development authentication on it.
Read docs/EXECUTION_PLAN.md, docs/PRODUCT.md and docs/ARCHITECTURE.md before changing invariants. Update proof and known gaps honestly. Coordinate file ownership between agents.
